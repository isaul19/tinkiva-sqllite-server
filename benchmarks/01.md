Escenario por base Cada base contenía:

- 10.000 registros.
- Payload de 256 bytes por registro.
- Aproximadamente 2,72 MiB de datos.
- Una tabla y un índice.
- 5 usuarios sin pausas:
  - 1 ejecutando UPDATE continuamente.
  - 4 ejecutando SELECT continuamente.
- Duración: 8 segundos.
- Pool predeterminado: máximo 2 conexiones por base. Los lectores ejecutaban consultas indexadas que
  devolvían 100 registros con su payload. El escritor actualizaba un registro por clave primaria.

El proceso vacío consumía aproximadamente 10,4 MB. ¿Cuánto consume una DB con 5 usuarios? Si
solamente existe una DB activa: Proceso vacío: 10,4 MB 1 DB durante la carga: 19,9 MB pico
Incremento observado: 9,5 MB Sin embargo, esos 9,5 MB incluyen costes iniciales del allocator,
runtime HTTP, buffers y primeras conexiones. No se repiten íntegramente por cada nueva DB. Cuando el
número de bases aumenta, el coste se amortiza: Escala RAM retenida por DB RAM pico adicional por DB
5 DB 3,87 MB 3,89 MB 20 DB 2,05 MB 3,11 MB 50 DB 1,85 MB 2,80 MB

Una estimación práctica para este patrón sería: Proceso base: 10–20 MB Por DB activa retenida: 2–3
MB Pico por DB activa: 3–5 MB Para producción aplicaría margen de seguridad: Presupuesto
conservador: 6–10 MB por DB caliente Así, para 50 bases activas simultáneamente: Medido: 151 MB pico
Presupuesto seguro: 300–500 MB RAM recomendada: 512 MB mínimo Cómodo en producción: 1 GB Pool de 2

Cinco conexiones consumieron unos 3,7 MB adicionales y rindieron peor. SQLite sigue teniendo un solo
escritor; agregar conexiones incrementó la contención. Para el patrón de 1 escritor + 4 lectores,
