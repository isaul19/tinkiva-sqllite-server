# Benchmark 01: carga mixta multi-tenant

Primera medición reproducible de TinkivaDatabase con múltiples archivos SQLite y una combinación de
lecturas y escrituras concurrentes.

> [!WARNING]
> Corrida obsoleta, conservada como registro histórico. Sus cifras se midieron sobre la versión previa
> a la ronda de optimización y con un arnés que abría una conexión TCP por operación, de modo que el
> throughput reportado describe al cliente Python más que al servicio. Las cifras vigentes están en
> [benchmarks/02.md](02.md).

> El análisis consolidado, las recomendaciones de RAM y las limitaciones se encuentran en
> [BENCHMARKS.md](../BENCHMARKS.md).

## Entorno de la prueba

- Fecha: 26 de agosto de 2026.
- Plataforma: Windows.
- Compilación: perfil Rust `release`.
- Duración por escenario: 8 segundos.
- Pool predeterminado: 2 conexiones por base.
- Proceso vacío: aproximadamente 10,4 MiB.

## Contenido de cada base

- 10.000 registros.
- Payload de texto de 256 bytes por registro.
- Aproximadamente 2,72 MiB de datos.
- Una tabla y un índice.
- WAL habilitado.

La preparación ejecutó `CREATE TABLE`, `CREATE INDEX` y una inserción masiva transaccional.

## Carga por base

Cada tenant recibió cinco usuarios sin pausas:

- un escritor ejecutando `UPDATE` parametrizados por clave primaria;
- cuatro lectores ejecutando `SELECT` indexados;
- cada lectura devolvía hasta 100 registros con su payload.

Con el pool predeterminado, los cinco usuarios compartían un máximo de dos operaciones SQLite
simultáneas por archivo.

| DB activas | Usuarios | RAM máxima | RAM final | Rendimiento | Latencia p95 | Errores |
| ---: | ---: | ---: | ---: | ---: | ---: | ---: |
| 1 | 5 | 19,94 MiB | 18,97 MiB | 1.001,6 ops/s | 20,68 ms | 0 |
| 5 | 25 | 29,84 MiB | 29,75 MiB | 2.658,6 ops/s | 14,18 ms | 0 |
| 20 | 100 | 72,54 MiB | 51,45 MiB | 2.511,0 ops/s | 61,03 ms | 0 |
| 50 | 250 | 150,57 MiB | 103,05 MiB | 2.498,0 ops/s | 156,28 ms | 0 |

## Coste incremental observado

| Escala | RAM retenida adicional por DB | Pico adicional por DB |
| ---: | ---: | ---: |
| 5 DB | 3,87 MiB | 3,89 MiB |
| 20 DB | 2,05 MiB | 3,11 MiB |
| 50 DB | 1,85 MiB | 2,80 MiB |

El primer tenant incrementó el proceso unos 9,5 MiB, pero ese valor incluye inicialización compartida
del runtime, allocator, buffers y conexiones. A escala, el coste se estabilizó cerca de 2 MiB retenidos
y 3 MiB de pico por base activa.

## Comparación del pool

| Pool por DB | RAM máxima | Rendimiento | Latencia p95 |
| ---: | ---: | ---: | ---: |
| 2 conexiones | 19,94 MiB | 1.001,6 ops/s | 20,68 ms |
| 5 conexiones | 23,65 MiB | 749,1 ops/s | 24,87 ms |

En esta carga, cinco conexiones consumieron más memoria y redujeron el rendimiento debido a la
contención del escritor. Dos conexiones por base fueron el mejor punto de partida.

## Comprobación con una base mayor

El escenario de cinco usuarios se repitió durante 15 segundos con 100.000 registros y aproximadamente
27,1 MiB en disco:

| RAM máxima | RAM final | Rendimiento | Latencia p95 | Errores |
| ---: | ---: | ---: | ---: | ---: |
| 19,99 MiB | 18,82 MiB | 923,9 ops/s | 22,39 ms | 0 |

La RAM casi no cambió porque SQLite carga páginas según las consultas, no el archivo completo.
